Agent orchestration lets the active agent organize work across Zuse without turning the parent conversation into an unreadable stream. Delegated work stays visible as normal chats, so you can open it, inspect its environment, and step in.

## Zuse's chat tools

Agents that Zuse launches receive Zuse's MCP server, which includes tools to work with other chats. Each message an agent sends this way is attributed to the chat it came from, and a chat can never message itself.

| Tool | What it does |
| --- | --- |
| `list_harnesses`, `list_models` | See which agents and models are available on a computer |
| `list_projects`, `list_devices` | Find projects and the computers that host them |
| `create_chat`, `create_chats` | Start one or several chats, optionally with a first prompt |
| `list_chats`, `get_chat`, `read_chat` | Check status and read transcripts, including chats this chat created |
| `send_message`, `send_messages` | Send a follow-up; it starts a turn when the chat is idle and steers a running turn otherwise |
| `wait_for_turn` | Wait until a chat finishes, needs input, or errors |
| `respond_to_input` | Answer a question a chat's agent is blocked on |
| `interrupt_chat`, `archive_chat` | Stop a running turn, or tidy up chats it created |

A new chat can be a standalone chat, visible in the sidebar, or a side chat attached to the current chat. The creating agent picks the project, computer, agent, model, reasoning level, access level, and whether to start in Plan mode. If it doesn't name an agent, Claude Code is used when available.

## Choose the right boundary

The most important choice is whether the work needs a separate checkout. A delegated chat works in the project folder unless the agent points it at an existing worktree, so two agents editing at once can collide. For parallel editing, ask for each task to run in its own worktree, or create those chats yourself in worktree mode.

| Boundary | Best for |
| --- | --- |
| **Separate chat in its own worktree** | Independent implementation, risky experiments, or work that may ship separately |
| **Chat in the same checkout** | Review, handoff, or a second approach that must see the same files |
| **Subagent** | Short bounded research or provider-supported specialist work |

## A reliable orchestration request

Tell the coordinating agent:

1. what can run independently;
2. which chats may edit and which are read-only;
3. who owns each file or subsystem, and which checkout each one uses;
4. what evidence each chat must return;
5. who integrates and runs final checks.

For example:

> Start an implementation chat in its own worktree and a read-only review chat. The implementation owns the parser and focused tests. The reviewer doesn't edit files. Bring both results here, resolve disagreements, and show me the final verification before any pull request action.

To pair devices or check a host from a script, or to run Zuse's MCP server outside a session, see [Scripting and agent tools](/serve/agent-cli/).

## Keep one integrator

One agent should stay responsible for the final state. It decides which findings to accept, checks for conflicts between chats, reviews the complete diff, and runs tests that cross ownership boundaries. Delegated agents should report what they changed and what remains uncertain instead of declaring the whole project finished.

## Permissions and autonomy

Starting and messaging other chats are tool calls like any other, so the active chat's access level and Plan mode apply. Each delegated chat runs with its own access level; choosing a different model changes who does the work, not what it's allowed to touch.

Before approving a delegated action, check the boundary, whether it should share a checkout, the agent and model, and the expected evidence. Permission to start a chat is not permission to accept its changes, merge it, deploy it, or take another external action.

For a standing coordinator that keeps issues, documents, and worker threads across days, see [Zappers](/composer/zappers). Continue with [Run agents in parallel](/composer/parallel-agents/), then learn how to [monitor and review delegated work](/composer/monitor-delegated-work/).
