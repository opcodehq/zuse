# Chat permissions

A new chat starts with the saved permission default. Its composer can select Ask for approval, Approve for me, Full access, or Read only. An existing chat retains its own configuration when the default changes. Read only remains selectable for existing restrictive workflows; it is not an automatic approval-judging mode.

The canonical run contract is `RunRequest.sandbox` plus `autoApprove`. Approval bypass requires **both** `danger-full-access` and `autoApprove: true`, expressed by `RunRequest::auto_approves_tools()`. A stale auto-approval flag cannot authorize bypass for a restricted run. The native composer and browser persist existing-chat changes through `setChatConfig`, so later queued turns use the saved posture. Unconfirmed saves fence new sends until the current mode has been read again.

| Selection | Codex adapter | Claude adapter | Zuse harness |
| --- | --- | --- | --- |
| Ask for approval | Workspace-write sandbox, network restricted, on-request approvals | Default CLI permission mode; permission callbacks ask through Zuse's input bridge | Approval-required tool policy |
| Approve for me | Workspace-write sandbox with the native `auto_review` reviewer | Native CLI `auto` permission mode | Not advertised; choose Ask instead |
| Full access | Danger-full-access sandbox and no wire approvals when explicitly opted in | Bypass permission mode when explicitly opted in | Full-access tool policy when explicitly opted in; sensitive-path checks still apply |
| Read only | Read-only sandbox; escalation approval requests declined | Plan permission mode; permission callbacks for tools are denied | Plan tool policy |

Claude's ordinary permission rules still apply before its callback. Its plan mode and permission callback are provider controls, rather than a uniform OS sandbox supplied by Zuse. The CLI sends write requests through the callback in plan mode; Zuse denies those requests. The adapter targets CLI 2.1.228, which is newer than the documented shell-write callback change in 2.1.212. See [Claude's permission evaluation and plan-mode documentation](https://code.claude.com/docs/en/agent-sdk/permissions).

Content questions remain interactive even in Full access. Tool approval questions accept only an explicit Yes for their own question ID; No, missing answers, and a dropped resolver decline the action. Read-only escalation requests do not ask the user to bypass that mode. Changes to the sandbox require a new native provider runtime, rather than silently reusing a process launched with different permissions.

ACP adapters select advertised permission modes through config options or the first-class session mode API. Restricted runs do not default to a bypass mode; Read only requires an advertised planning/read-only mode. An agent that rejects the selected mode cannot start the prompt. Permission callbacks are scoped to the current session: foreign and missing owners are cancelled, content questions remain interactive, and only explicit Full access automatically chooses an allow option. That automatic choice prefers one-time permission over a persistent rule and never falls back to an unknown option kind. See the [ACP session mode contract](https://agentclientprotocol.com/protocol/v1/session-modes).

The HTTP/SSE adapter applies permission rules to each provider session, including resumed sessions, without editing server-wide configuration. Both supported wire generations receive their own schema: v1 uses `permission/pattern/action`, v2 uses `action/resource/effect`. Non-read-only sessions ask for tool execution while allowing file inspection and content questions; Full access answers owned permission requests once. Read only, including the built-in planning agent, denies unknown/write actions and permission escalations. The provider's default protected environment-file patterns remain denied. Mode, sandbox and agent changes cannot silently reuse a runtime with older settings.

A resumed session whose saved rules do not match must successfully apply an update before another prompt starts. Some older 2.x servers expose session creation rules without a session-update route; they can continue sessions already carrying the requested rules, but changing an older session's policy requires a server version with that route. Failure is reported instead of running under unconfirmed permissions.

The native Pi adapter installs a per-process access extension through its public `tool_call` and `user_bash` hooks. File inspection (`read`, `grep`, `find`, `ls`) remains available. Ask for approval confirms every other tool, including managed delegation/plugin tools, through the existing input bridge. Only an explicit Yes to the matching question authorizes execution; rejection, cancellation and a dropped input resolver deny it. Full access bypasses tool approval only through the shared run predicate. Read only denies every non-inspection tool and direct shell command, including when `autoApprove` is stale. These are provider tool controls, rather than uniform OS isolation.

Restricted Pi runs disable ambient extension discovery because those extensions can replace inspection tools or execute arbitrary startup code outside the approval hooks. The explicitly installed Zuse access/MCP bridges still load; global extension settings remain unchanged. Full access retains the user's installed extension discovery. A per-process readiness nonce must appear in Pi's extension command catalog before Zuse admits a prompt, and that internal command is omitted from the product's available-command list. A failed guard load stops the run. Actual Pi 0.85.1, using a local mock model and the real file-writing tool, verifies approval, rejection, dropped answers, explicit bypass, stale flags and read-only denial without API usage. This does not establish the permission behavior of arbitrary trusted extensions in Full access.

Automatic approval judging uses the native Codex and Claude reviewers already wired by `SandboxLevel::Auto`; unsupported harnesses disable that choice, and provider escalations still ask. Uniform OS isolation for Zuse tools, the remaining native SDK adapter permission audit, and physical desktop/live installed-provider acceptance remain open gates. Subprocess fixture coverage verifies wire policies, callback routing and decisions; it does not prove OS isolation of installed tools or every provider integration.

Saved approval rules live on the execution host, in `journals/permission-rules.sqlite` inside the active engine profile. A typed `ToolApproval` marks provider approval callbacks; content questions and private-secret questions carry no authority to create a rule. Eligible prompts offer **Always allow in this chat** and **Always allow in project**. A grant matches the provider-qualified tool, canonical checkout directory and complete structured input exactly. JSON object key order is canonicalized; shell prefixes, wildcards and truncated display previews never match. Project IDs share a rule collection across project chats, with a canonical-directory fallback for project-less chats; exact checkout matching keeps relative actions in different worktrees separate.

Evaluation runs in the engine input bridge: read-only denial → native automatic-review escalation / forced prompt → chat override → project rule → ask. Read only declines callbacks even with a saved allow and a stale `autoApprove` flag. Sensitive paths, credential/login operations, plan exit and declared privilege escalations stay interactive and cannot create persistent grants. Existing provider sandboxes and plan-mode gates remain in force. Native review escalations cannot be silently approved by a saved grant. Missing ownership, replaced runs, malformed/multiple answers, unavailable rule storage and audit failures fail closed.

The composer's **Agent access → Saved permission rules…** inspector lists the current project's defaults plus this chat's overrides. It can change an exact rule to Allow, Ask or Deny, move its scope, remove it, and refresh recent activity. Scope moves that conflict with an existing rule fail without overwriting either rule. `ListPermissionRules`, `UpdatePermissionRule` and `RemovePermissionRule` derive project ownership from `chatId` on the target execution device; callers cannot supply an arbitrary project key or modify another chat's private rule. Rule mutations commit atomically with their audit entries. Request decisions include an input digest, sandbox, source and matched rule ID; the inspector returns the latest 100 activity entries while the full local audit remains in SQLite. Rules affect callbacks the provider sends to Zuse: Full access and native reviewers can execute actions without emitting an approval request, so the local ledger is not a complete provider execution log.

ACP saved grants use an unambiguous one-time allow option and the complete tool-call context, including its kind and `rawInput` (excluding the transport-only `toolCallId`); unknown/incomplete callback schemas remain interactive. The HTTP adapter stores exact resource/metadata requests and always sends a one-time wire reply. Pi's installed access guard marks its own confirmations with its per-process readiness nonce; ordinary extension dialogs do not acquire approval authority. Native Zuse, Codex and Claude callbacks retain full inputs independently of display previews. The engine keeps matching metadata in the parked request and strips it from the published question; transcripts keep display copy/options rather than a second raw tool payload.
