Zuse vs T3 Code — desktop performance

Both desktop apps, the same Mac, the same seeded chat history and the same measuring tool. On the desktop, Zuse opens about twice as fast and uses well under half the memory; T3 Code types slightly faster. Over a 3G connection T3 Code loads first and pages older history faster, while Zuse reloads, replies and reconnects faster. The benchmark also found an idle-CPU bug in Zuse with many chats, now fixed.

The idle-CPU bug Zuse had with 20 chats

Symptom. With 20 chats, Zuse burned ~29% of a CPU core while idle and frontmost — against ~1% with one chat, and ~6% for T3 Code.

Cause. While the window is active, the shell marks the selected chat "seen" during render by stamping last_seen_at = now. A chat counts as unseen while last_message_at > last_seen_at. When the last message is dated ahead of this clock (another device's clock skew, imported history), it stayed unseen after every mark, so it was re-marked on every frame: each mark notified app state and rebuilt the whole window, ~64 times a second, and sent a markChatSeen request to the engine. In the seeded data, chats C07–C19 were dated after today, and C19 opens at launch.

Fix (PR #188). Seeing a chat covers its latest message, so the seen stamp never lands before last_message_at — clamped in the shared document layer (every client) and stamped the same way by the desktop, which sends it to the engine.

Result. Idle CPU with 20 chats: ~29% → ~1%. Re-renders: ~64/s → ~2/s.

How this was measured

  • Machine. Apple M4 Pro (14 cores, 48 GB), macOS. Other apps stayed open in the background; treat numbers as same-machine relative comparisons.
  • Builds. Zuse release build of main at 9398cf44 (includes the local-only release change, PR #167); the fix is PR #188 (bfd8e2b2). T3 Code 0.1.9 desktop (Apple Silicon), notarized "T3 Tools, Inc.", SHA-512 verified against its update manifest.
  • Isolation. Each app ran from throwaway profiles with its home folder redirected; real profiles untouched (checked by timestamps). Same 1600×1000 window, minimal PATH (no real agent CLIs), T3 Code telemetry off, a local fake Claude provider.
  • Data. Identical text, roles and timestamps in both apps: Zuse through its own transcript importer, T3 Code through its server plus its database. Verified by reading every message back.
  • Open app → ready to type. From process start until a typed probe character appears in the composer, read off the screen (ScreenCaptureKit + Vision), on the system uptime clock.
  • Memory and CPU. Physical footprint and CPU time of every process belonging to the app (Zuse: 1 process; T3 Code: 6), sampled at 2 Hz for 20 s after settling.
  • Typing lag. 40 keystrokes, time until each appears on screen. Open / switch chat. Click a sidebar row, time until that chat's unique last message is on screen. Scroll. 120 wheel steps at 60 Hz; frames slower than 33 ms and the longest gap.
  • Tool. ademark-native, the measuring helper from the ADEMark benchmark, built from source and run with its own Accessibility and Screen Recording grants.

Caveats and corrections

  • Correction: early T3 Code runs were slowed by a macOS "Keychain Not Found" dialog that the isolated home folder triggered (4.4 s launches, a stuck splash screen with big chats). Those results were discarded; T3 Code now launches with --use-mock-keychain and all its numbers come from clean reruns.
  • History was imported, not produced by real agent turns; real chats can behave differently.
  • One T3 Code run (20 × 5,000, run 3) lost its window after launch, so it has no in-app tests; its launch counts. Its first switching run was slower (~410–500 ms vs ~185 ms later) and is in the median.
  • The measuring tool's typing-lag probe left a draft "ademarkqz…" chat in T3 Code's benchmark profile (not a real one).
  • Post-fix Zuse runs on 20 × 1,500 ran under heavy machine load (load average 18–30); their launch and lag figures are noisy and not used, only their idle CPU.
  • The 3G section is the earlier browser-UI benchmark (T3 Code 0.1.7, an earlier Zuse build), included for completeness, not rerun here. Not run at all: the ADEMark suite itself (needs a dedicated macOS account), battery and GPU.
