# Interactive visuals

Agent `show_visual` publications are persisted as sandboxed Luau programs and assets attached to the conversation. The desktop retains its existing native visual renderer. The browser now opens the same programs through an execution-host runtime, instead of showing only a visual label.

## Browser behavior

Open visual loads a transient session. It renders stacks/grids, rich text, statistics, tables with fixed/flexible column widths, cell alignment, hover rows and empty cells, buttons, tabs, switches, sliders, links, and bar/line/area/scatter charts. Charts support multiple series, gaps, negative values, explicit domains, stacking and horizontal bars. Canvas draw functions run on the execution host and return themed vector paths/text; browser canvases support pointer input, click handlers, responsive dimensions and paced animation. Buttons, switches, tabs, sliders, links and interactive canvases are keyboard reachable. Enter/Space uses toolkit activation; sliders support arrows, Page Up/Down and Home/End, and keyboard canvas activation targets its center. Controls expose roles, current values and focus feedback. This does not establish complete screen-reader acceptance. Closing or reopening a visual explicitly discards that view's interactive state. The stored program and assets remain available in conversation history.

Every control names the displayed revision and an opaque lease. The host accepts only handlers and argument kinds present in that revision, validates option/range values and rejects stale inputs. Slider input coalesces only for a compatible current slider; topology/range changes retire queued slider input. Keyboard changes build on the latest requested slider value, including input that returns to the original value while a callback is pending. The owner stream supplies canonical trees. Control requests are never automatically retried. Errors with uncertain delivery require reopening; a callback failure retires the sandbox because it may already have changed state.

Visual sessions capture their execution host. Opening requires the visual to belong to the requested host-owned conversation, and source/assets load through the attachment path jail using an engine-issued identity. Navigation or connection changes cancel browser owners and discard late responses. Canvas work is paced, limited to one in-flight draw per view, scheduled fairly between canvases, and paused when its surface stops painting or settings obscure the transcript.

## Motion policy

Desktop and browser share the same `ReduceMotion` values and resolver in `zuse-protocol::presentation::motion`; native settings keep their existing serialized format. Browser Appearance settings persist System/On/Off and the independent background-pause preference locally. A single page observer reports system reduced motion, visibility and focus changes without polling or engine requests. This drives GPUI animations, voice orbs and visual drawing; voice capture no longer installs a second motion observer. Hidden documents stop visual animation draws and hide the voice orb without ending the audio call. Reduced canvases still draw for changed content, size or pointer input.

## Runtime boundary

A thread confines each Luau runtime; no interpreter or native audio/filesystem library is linked into WASM. Existing interpreter memory/time budgets remain active. All RPC services for one engine share eight runtime slots. Command and output channels are bounded; an output subscriber that falls behind cannot block a worker indefinitely. Frames are capped at 4 MiB. Closing the subscription retires its lease and releases the sandbox. Engine/account runtime shutdown closes all leases and refuses new sessions. Programs, media and interactive state are not mirrored into browser persistence.

The host advertises `visual-sessions-v1`. `OpenVisual` is an owning stream; `ControlVisual` and `DrawVisual` are unary operations. The three methods route to the selected execution computer through the existing relay transport. Draw functions can mutate program state, so drawing is deliberately excluded from uncertain-delivery retries too.

## Evidence and remaining work

Three engine scenarios cover transcript membership/host selection, isolated state, stale and invalid controls, actual canvas output, callback failure, owner-drop cleanup, runtime capacity and shared shutdown. Three viewport scenarios cover host/revision ownership, slider coalescing without duplicate callbacks, navigation retirement, rapid keyboard reversal/coalescing, reduced/hidden drawing, stacked negative bars, scatter geometry and line gaps. Native Linux compilation and the production WASM bundle pass. This client milestone reuses the previously built host runtime; its engine behavior and RPC contract are unchanged.

A disposable real server runs a scripted ACP provider that publishes through the actual `PublishVisual` RPC during its agent turn. The compiled browser opens the actual host Luau session and exercises pointer controls, keyboard activation/traversal and slider keys against canonical host state. The retained scenario also renders a fixed-width/aligned table with a missing cell and confirms that reduced motion stops animation RPCs. Closing stops drawing. No visual responses are mocked; the provider itself is a fixture, not a live third-party provider. Current client evidence is `.context/visual-parity-{viewport-tests,visual-tests,policy-tests,adapter-tests,native-final-check,web-final-build,browser-final-check,browser-frame-check,final-format}.log`; retained host evidence is `.context/visual-session-{engine-tests,server-build}.log`, `.context/visual-session-browser-acceptance.json` and `.context/visual-session-final.png`.

The disposable browser scenario is retained as `node scripts/acceptance/visuals.mjs`; it requires the built host binary, `dist/web`, Node and `agent-browser`. Its ACP and browser observers live under `scripts/acceptance/fixtures` and never modify the running preview or its profile.

Browser 3D scenes/shaders, complete chart axes/hover and layout parity, full screen-reader/accessibility acceptance, physical input/GPU and actual paired-device rendering remain open. Desktop scene/shader rendering remains available. Embedded web previews are implemented separately; paired preview tunneling remains unfinished; see `browser.md`. This milestone does not establish full native/browser visual parity.
