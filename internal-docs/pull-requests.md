# Pull requests

The native app retains its dedicated PR board and detail windows. The browser now has a PRs tab in the right sidebar, scoped to the selected project's GitHub repository and execution device. Authored, Reviewing and All filters use the engine's existing paginated service. The board adopts repository renames from the first provider page, deduplicates overlapping pages and rejects mixed-repository pages.

The native board follows the Plugins page layout: title and subtitle, then a short search on the left, refresh and the repository picker on the right, and the options menu at the far edge. Open, Merged and All lifecycle tabs sit underneath; All includes closed, unmerged requests. Its options menu contains the personal views and sort order. Each row keeps one two-line shape at every width: the title and a short age (`5m`, `1d`, `8w`, `9mo`, `1y`), then author, number, CI and status beside the diff counts. Avatars use GitHub-provided CDN URLs; unavailable or failed images fall back to initials without repeated requests. Search and personal views apply to the pages already loaded, and additional pages can be loaded from the list footer. The browser's relationship filters remain unchanged.

Native viewer tabs use the PR's lifecycle icon and color in both the board pane and chat panes. Summary, Code and Activity share a compact floating navigation bar with a translucent blurred backing. Timeline is available from the header menu; it groups commits by date and shows their titles, authors, copyable SHAs and available line counts. Selecting a commit opens its diff in Code; All changes returns to the complete PR diff. Statistics cover the first 100 commits when GitHub provides them, and listings of 100 or more offer the full history on GitHub. Older engines show an unavailable timeline rather than an empty history. The Code view uses a unified, wrapping diff for narrow panes. Description images align with the text and fit the available column width while retaining their aspect ratio; screenshot tables retain their wrapping gallery layout.

The navigation's surrounding fade separates it from scrolling content while the diff extends behind it. Feedback previews retain whole blocks and compact ordinary tables; the Activity view shows the full comment. Simple wide Mermaid chains in PR descriptions can use a vertical preview in narrow columns without altering the source or copied text.

Browser detail shows the description and discussion as Markdown, CI checks, and a virtualized unified diff pinned to the displayed head and base revisions. When a newer detail changes either revision, the previous patch and its pending read are retired. Opening another checkout retires old requests. Archived threads browse using the owning project's live checkout without restoring the thread.

Comments submit explicitly through the existing host GitHub CLI service. The header menu also offers title and description editing and reviewer requests; status actions include draft, ready, close and reopen. GitHub enforces permissions. Edit bodies are sent to the CLI on standard input, and failed or uncertain edits retain their form for review. Draft comments are retained across PR navigation in memory, with up to 32 saved drafts. Losing a receipt preserves the text and refreshes the discussion; it never automatically posts again. A late receipt cannot clear a newer draft. Cache entries and in-flight reads are invalidated even when the write times out, since the remote may have accepted it.

Both native and browser Changes panes also expose Create pull request in their shared Git panel. The form takes title, description, optional base branch/repository and a draft switch. Blank base uses GitHub's default branch; blank repository uses the publishing repository's parent for a fork, otherwise the publishing repository. Creation requires a published upstream and no unpushed commits. The engine revalidates the thread, canonical checkout and displayed Git revision, then checks the published source branch SHA. The body is JSON on stdin, never shell text. Cross-repository requests supply the owner-qualified head and source repository name. The successful receipt offers Open created PR.

Creation is a mutation within `GitWorkspaceAction` and is never automatically retried. A lost or invalid receipt retains the form and tells the user to inspect PRs before submitting again. A successful response clears the form only if its text still matches the submitted draft. GitHub can advance a branch between the source check and creation: the response head is checked too, but this is not an atomic remote compare-and-create operation. Such a mismatched receipt is treated as uncertain.

A turn whose agent runs `gh pr create` leaves a live pull request card after its work, before the reply. While the command runs it shows the step (committing, pushing, opening). Once `gh` prints the URL the card follows the PR: title and state, then "Merge into <base>" with the branch's commits beside the base's since they forked (lanes from the shared history layout: the branch in the accent, the base muted, branches merged into the base green), then the next step. Conflicts list the files with each region's two sides on hover and offer Resolve conflicts. Failing checks offer Fix checks, a draft offers Mark ready, and a ready PR offers Merge with the three methods. A merged PR links to GitHub. Resolve and Fix send the same repair prompt the session card stages. They send it as the next message, or append it after a draft in progress without sending. The card refreshes every 12 s while something is pending and every minute otherwise, and only for the selected chat. Above the input, the composer shows the chat's PR (number and the card's latest reading) on the left and, while the PR is open, a small Auto-fix button on the right that toggles the PR watch's auto-fix and shows the golden pixel loader while a follow-up runs.

The graph comes from `GetBranchGraph {cwd, base, fetch, limit}` on the chat's device. It optionally fetches the base, resolves its remote-tracking ref (else the local branch), counts ahead/behind and finds the original fork. That is the first parent of the oldest first-parent commit only the head has, so it survives merging the base in. It lists both sides since then and previews the merge with `git merge-tree --write-tree`. Conflict regions come from the merged blob's markers, with up to six files and three regions each, and name who last changed the file on the base. Git older than 2.38 reports no preview, and the card falls back to GitHub's mergeability. The call never touches the working tree, index, HEAD or a local branch. A fetch moves only the base's remote-tracking ref.

Focused checks cover literal JSON bodies, same-repository creation, fork-parent targeting, unpublished-head refusal, timeout cache retirement, board paging, device routing, revision changes, stale responses and comment uncertainty. They use scripted provider responses and GPUI state, not live GitHub writes. Existing real-Git checkout admission and shared panel checks remain applicable. Hosted creation/comments and physical native/browser rendering are separate acceptance gates. Browser agent handoff and an aggregate multi-repository board remain unfinished.

## PR watch and automatic follow-up

A chat's PR card and PR pane register an engine-owned PR watch, and so does the chat itself when it opens a PR: once a turn whose `gh pr create` printed a PR URL completes, or the conversation's Create PR flow succeeds, the engine adopts that PR with auto-fix on. This works with no window open (Zapper workers, unattended tasks). Adoption never overrides an existing watch's choice, and plan-mode chats only observe. Watching survives closing the pane and restarting the engine. **Watch CI** pauses/resumes observation; **Auto-fix CI and reviews** separately grants permission for up to five follow-ups per PR, including commits and normal pushes. Restart auto-fix explicitly grants a fresh budget after reviewing the previous repairs. Pausing prevents future admissions; an admitted agent turn continues under the chat's normal controls.

`ObservePrWatch {chatId,url}` creates observation without changing existing preferences. `SetPrWatch {chatId,url,enabled,autoFix,resetAttempts?}` changes permission, and `WatchPrWatches` streams status, failure sequence, attempt count and errors. All three route to the chat's host via `targetDeviceId`; `pr-watch-v1` advertises support. Watches and reservations live in the profile's `pr-watches.sqlite`, separate from UI settings. They do not transfer repair permission to a different host or account profile.

The engine reads PR summaries without fetching or changing Git refs. Enabled background watches retain demand on the same summary resource as visible views. Repair policy checks the cached state every 20 seconds while pending and every minute when settled; provider refresh cadence is shared with foreground views. Failures back off up to 15 minutes. No UI subscription is needed to keep an enabled watch alive. Closed PRs, changed PR identities and moved chats/checkouts stop watching; drafts and branch changes pause automatic repair. Check fingerprints include the PR URL, commit, job identity, start/completion times and conclusion, sorted independently of provider ordering. A terminal conclusion takes precedence over stale running status; pending checks with no conclusion cannot trigger repair. Repeated snapshots do not duplicate a repair, but a new run or commit can consume another attempt.

Automatic repair requires a hosted, unarchived, writable chat, an empty unpaused queue, no pending commands or active turn, and a clean checkout on the observed branch and exact PR commit, publishing to the PR source repository (including forks). Multiple push URLs are refused. Other active conversations sharing the checkout also block admission. Within one host profile, another watch cannot enable auto-fix for the same PR or checkout. Log preparation rechecks both the PR failure fingerprint and local commit, and admission rechecks the current chat permissions and watch generation. Permission comes from the current chat configuration; automation never upgrades sandbox or approval settings.

Failed GitHub Actions logs are fetched with literal argument arrays through the existing bounded process runner (20-second deadlines, at most eight checks and 48 KiB per log). Other providers are identified as requiring manual log inspection; remaining or truncated logs are explicitly marked. Jobs that fail without readable logs contribute an unavailable-log note so the agent can investigate workflow or infrastructure blockers. Authentication, rate-limit, process startup, I/O and timeout failures still back off before admission. Logs travel inline as quoted JSON in a data block that cannot activate native composer commands. Prompt log context is capped at 16 KiB after escaping so agent CLI argument limits are respected; the prompt marks omitted context and directs the agent to retrieve complete failing logs before repairing. The repair prompt asks the agent to reproduce and verify, commit and push normally, and stop on a changed head, rejected push or unsafe repair. It explicitly forbids force-push (including force-with-lease), history rewrites, branch switches and merging. The watcher itself performs no Git mutations. This prompt does not replace the harness's existing permission system.

A follow-up addresses everything outstanding at the observed head in one prompt: failing CI (with logs), a merge conflict against the base (`mergeable: CONFLICTING`, keyed by head and base commits; the agent merges the base in, never rebases), and review feedback. Feedback is reviews with text or changes requested and comments in unresolved, non-outdated review threads; top-level PR comments (mostly deploy and coverage bots) ride along with a follow-up but never start one. All of it comes from anyone but the PR author and the signed-in account (so the agent's own replies never retrigger it). Inline threads are read only once a reviewer posted a review not yet followed up on; text-less reviews whose threads hold nothing to address are settled without a follow-up. The engine waits 90 seconds after the newest unaddressed comment so one follow-up answers a whole review burst. Feedback travels as bounded single-line JSON (30 items, 12 KiB) in a quoted data block; the agent addresses actionable items or explains why not in the chat, and never posts, replies to or resolves PR comments. Every CI fingerprint, conflict and comment is remembered (newest 2,000), so nothing is sent twice. The status reports what the latest follow-up addressed.

Each follow-up is reserved durably before dispatch. Five reservations exhaust the budget even if delivery fails. A crash or uncertain dispatch pauses auto-fix and preserves the fingerprint and count; automation never replays an uncertain repair. The chat contains the delivered repair prompt and agent results. Shared protocol notification baselines feed the existing attention sound and desktop/background preferences across all online supported devices, independently of the selected chat. Initial snapshots seed silently, and muted transitions are consumed rather than replayed later.

The implementation follows the original behavior in `swarajbachu/zuse` PRs #586 and #587 (`pr-watch-controller`, `pr-watch-policy`, `pr-watch-repair`, `PrAutoFix`, and the failing-check artifact contract/server log fetch). The Rust port owns polling and repair reservations in the engine instead of browser local storage. Native/chat controls and engine/RPC behavior are implemented; browser viewport controls, non-Actions log adapters, physical desktop banner delivery, and a live agent repair/push against hosted CI remain acceptance work.

The `pr-ci-watch-fixture` native example renders the production shell and PR card against an isolated WebSocket RPC fixture. It captures watching with auto-fix off, auto-fix at 1/3, and the paused 3/3 restart state in dark and light appearances. Its data is synthetic; it does not run an agent, contact GitHub or push Git refs. Build with `cargo build -p zuse-ui --example pr-ci-watch-fixture --features browser-fixture,pull-request-fixture`, then run the example with an output directory on an isolated Xvfb display. The screenshots in `images/pr-ci-watch-*.png` show actual native rendering, not design mockups.

## PR detail and loading

The pane is a rounded inset card like the conversation. No rule separates its tabs from its header row, which carries the state icon, number, Merge (Ready for review on a draft), a GitHub link and an overflow menu (copy link or branch, Add to chat, star, refresh, Convert to draft, Close or Reopen). Choosing a merge method is the confirmation. While a pull request is blocked, Merge still opens: the methods stay dimmed under the reason, and Enable auto-merge or Force merge unlock them for that purpose. Force merge is an ordinary merge attempted before checks pass; it never passes `--admin`, so GitHub still refuses what branch protection requires. Conflicts offer neither. Merge and auto-merge requests carry the displayed head SHA through the RPC to `gh pr merge --match-head-commit`; a changed head refuses the merge. GitHub still enforces repository permissions and merge requirements.

Mermaid fences in the description and comments draw as diagrams through the same bounded renderer as chat, off the UI thread, with a source toggle and click-to-enlarge. A fence that can't be drawn stays as source with a warning.

Inline review comments in Discussion show `path:lines`, Resolved or Unresolved, Outdated, and the last few lines of their GitHub diff hunk, with the commented lines marked.

Summary shows the title, then Branch, Status, Reviews and Checks facts, then quiet sections separated by space: a clamped Description with Show more; Checks with failures first and a terminal loader on anything still running; and Feedback from everyone but the author, where each row and Add all stage context for chat without sending. Hand-off, verification platform and Auto-fix CI and reviews sit in a collapsed Agent section. Auto-fix is one switch; its repair budget and commit/push permission are explained in its tooltip.

PR reads have a 45-second UI deadline and retain the last successful details on failure. Active detail tabs and transcript cards subscribe to shared engine PR summaries. Pending checks refresh about every fifteen seconds, settled open PRs every minute, and terminal PRs every ten minutes, with small per-resource staggering. Description, ordinary comments, reviews and checks arrive without waiting for paginated inline review threads. Full discussion and revision-bound diffs remain separate reads. The card publishes metadata before loading its local branch graph and never starts a network fetch for that graph. Sidebar resolution uses an unqualified branch with `gh pr list --head`, then validates the returned source owner; the CLI does not support owner-qualified head arguments. Missing PRs use a five-minute negative cache, and existing PRs a one-minute cache, subject to context polling and failure backoff. Explicit Git actions and new PR subscriptions invalidate discovery immediately. Production branch-context reads are briefly shared across subscribers for the same checkout.


The provider read cache has 256 entries and includes an opaque credential namespace; account switches and token changes cannot reuse another account's in-memory results or rate-limit pause. Credentials are never written into cache keys on disk. Confirmed sidebar branch links are persisted separately by account, checkout, branch, upstream and remote; a restored link renders before provider refresh, with its original timestamp. Environment-token authentication disables this disk persistence. The board retains its existing account-scoped first-page store.

The durable background CI watcher shares the provider summary cache with visible consumers. Immediately before automatic repair, it still performs an uncached CI read and validates the exact checkout and commit. Foreground inspection updates without enabling background monitoring or repair. Auto-fix is on by default only for PRs a chat opens itself, stays bounded, and a watch without auto-fix offers Stop watching.

Sidebar lookup failures are explicit frames: a previous PR and its successful timestamp survive with an error, and an initial failure is distinct from a successful no-match lookup. Native sidebar rows show a warning with the provider failure reason.
