# E2B managed-base publication

The operator implementation is `infra/cloud/build-e2b-managed-base.mjs`. It produces an **uncertified** private template candidate. It does not register a managed base, enable a candidate, send model requests, or use account credentials inside the template. No remote build or sandbox has been executed for this implementation yet.

## Inputs and SDK

Use Node 22.19 or newer and the pinned E2B SDK **2.62.0**. The publisher checks the SDK package version and official `dist/index.mjs` SHA-256 before import. The package tarball SRI and module digest are constants in the source. Download from the public registry, verify the tarball SRI, and install dependencies without lifecycle scripts in an isolated operator directory. The root operator supplies `E2B_API_KEY` privately; it must not be added to bundle files, template environment, reports, or shell output.

The input is the ordinary hash-verified complete native bundle, including Codex companion assets and an immutable OCI base image digest. Staged installation requires the current installer; an older captured bundle that lacks stages is rejected. Creating a new bundle changes its hashes and requires a fresh review. The plan records builder, helper, installer (through bundle), runtime, Supervisor, harness and SDK pins.

The official SDK supports `Template.setStartCmd(startCommand, readyCommand)` and separately reports template/build identifiers. See the [E2B build-system documentation](https://e2b.dev/resources/introducing-build-system-2-0) and [SDK package metadata](https://registry.npmjs.org/e2b/2.62.0). The actual pinned SDK was composed offline in a test with network calls disabled. Its original file hash routine reads each whole file and constructs a second byte array; the largest current native payload is 319,346,888 bytes. That path does not fit the 512 MiB operator limit. `e2b-streaming-hash.mjs` therefore uses an instance-only, exact-fingerprint-checked hash/serialization seam: sequential 1 MiB reads produce the identical SDK COPY hash and payload SHA before the first build request. Only allowlisted literal regular files are accepted; input or instruction drift rejects. The upstream SDK package is unchanged and retains its disk-spooled tar and streaming PUT. Four parity/fence tests compare the complete serialized request with the unmodified pinned SDK, including binary content and source modes 0444/0555/0600. Unknown SDK methods reject before mutation.

## Image lifecycle

1. The template copies only allowlisted verified bundle files and the portable preparation helper, as root-owned files.
2. Installer `layout` installs packages and payloads, then publishes a protected hash-bound `layout-receipt.json`. It does not claim readiness.
3. The portable helper starts one temporary owned Supervisor, executes installer `prepare`, and requires the existing real image/native/code-mode/GitHub gates and clean account-free manifest. It reaps that temporary process and proves no task-user process remains before writing `base-prepared.json`.
4. Before finalization, the build seals all nine managed runtime/launcher/Supervisor/repair/recreation files and both preparation/boot helpers into a root-protected receipt under `/opt/zuse/base`, outside `/usr/local`. E2B starts a root-owned foreground boot helper there using isolated Python (`-I -S -B`). It permits only the exact provider's `0777` permission rewrite or the original target modes, verifies all bytes/ownership/paths before changing any permissions, then restores only the four necessary `/usr/local` ancestors and nine allowlisted files. Unknown library files/bytecode, symlinks, aliases, hardlinks, changed bytes, wrong owner and unrelated mode drift reject. It refuses an already active task-user process and execs the existing Supervisor, which drops to the task user before resident initialization.
5. The bounded read-only `readyCmd` uses the protected helper, revalidates the seal and strict permissions, and runs the unchanged portable readiness checks: prepared receipt, protected artifact hashes, clean manifest and current idle private ping. It performs no preparation or model request. `bootSealVerified` and the exact boot-helper SHA must match the source plan. OCI unpacking may change inode/device; byte hashes remain authoritative, with metadata rechecked within each read.

The ordinary installer default (`all`) retains the existing Boxd/Boat path. The shared installer includes the separately tested canonical GitHub wrapper directory-mode correction: its root-controlled directories remain traversable under umask 077. Root owns that fix; the staging seam preserves it.

## Proposed bounded live operation — root review required

First generate the read-only plan locally or on the operator host:

```sh
node infra/cloud/build-e2b-managed-base.mjs \
  --bundle /private/reviewed-bundle \
  --base-image 'reviewed-image@sha256:EXACT_DIGEST' \
  --output /private/e2b-one-shot.json
```

For an actual run use `infra/cloud/run-e2b-publication.py` with `--node` pointing to Root's trusted remote Node executable and `--node-sha256`, `--publisher`, `--bundle`, `--base-image`, `--sdk`, `--output` and a private SSD-backed `--tmpdir`. Its default invocation records a credential-free source/bundle/SDK/Node-bound plan. Root must review that exact plan digest, then invoke the same launcher with `--live --plan-sha256 DIGEST`; the key is inherited only in that live child environment. Its fsynced one-shot UUID/name precedes the Node process. The **1200-second outer deadline includes uploads**, rather than starting after `buildInBackground` returns. It holds the original leader unreaped through group retirement, adopts/reaps SDK observer children on timeout or normal/nonzero exit, then runs a separate **90-second read-only reconciliation**. This reconciliation lists the exact original unique template and original sandbox operation metadata; it never creates, retries, resumes, or deletes. Absence is point-in-time only and never upgrades an uncertain operation to cleanup-verified.

The live handoff must be started through `e2b-publication-unit.py`, using the Root-reviewed launcher plan and its separate resource plan digest. Its default invocation prints a no-effects plan. Explicit `--approve-plan-sha256` starts one transient unit with MemoryMax 512 MiB, swap zero, CPUQuota 50%, TasksMax 128, OOMPolicy kill, KillMode control-group and a 1500-second service deadline. Only the inside-unit process may read `E2B_API_KEY` privately from the existing staging worker environment, after verifying the actual cgroup limits and all pinned source/SDK/Node inputs. The key is never placed in unit properties, argv or reports. SDK spools use the explicit private SSD TMPDIR, not `/tmp`. An OOM or service deadline remains uncertain; a persistent intent is not permission to retry.

The underlying publisher's same arguments plus `--live --sdk /private/pinned-e2b/dist/index.mjs --retain-artifact` permit **one** private uniquely named template build (900-second observation deadline) and **one** fresh proof sandbox (600-second TTL), with two CPUs and 2048 MiB configured for the template. All SDK request retries are disabled. Provider-specific billing/build limits must be reviewed before this step. No second sandbox, model credentials, task, candidate registration, promotion, arbitrary registry push or live account login is authorized by this plan.

Before either mutation the publisher fsyncs a private one-shot intent. A lost mutation response is uncertain: never rerun the report or mint a replacement automatically. The operator must reconcile the recorded unique name and operation before approving another attempt. Public reports contain safe identifiers, static error codes and proofs. A provider build failure first fsyncs a private `0600` diagnostic containing its error state and bounded last-100 logs, then publishes only a static stage/code and diagnostic hash/size before original-template cleanup. Failed diagnostic persistence leaves cleanup-required rather than discarding the original evidence. Raw private diagnostics must not be published or printed.

On success, verify exact template ID/build ID, private ownership and build count one; create the proof sandbox once with operation metadata; recheck template identity; validate current resident readiness, runtime SHA, strict clean manifest and actual canonical GitHub shim/login-shell proof. Delete the owned proof sandbox and verify absence. Retain the template only on explicit request and complete successful proof. Failure paths delete only ownership-verified resources and verify absence; ambiguity produces `cleanup-required` and prevents a clean-success claim.

Template references are mutable provider objects. The SDK/API exposes only `templateID` for sandbox creation; the server resolves an identifier/tag to its current build. Snapshot references also resolve to template/tag pairs. The implementation does not invent a create-by-build parameter. See the pinned primary [sandbox creation handler](https://github.com/e2b-dev/runtime/blob/78d5ff91515b58a9bd2d0b28b14f80428c63d15e/packages/api/internal/handlers/sandbox_create.go#L154) and [snapshot handler](https://github.com/e2b-dev/runtime/blob/78d5ff91515b58a9bd2d0b28b14f80428c63d15e/packages/api/internal/handlers/snapshot_template_create.go#L260).

The report binds `artifactId=templateId`, `providerArtifactVersion=buildId` and `providerArtifactBinding:{version:1,mode:"private-single-build",artifactId,artifactVersion,artifactName,runtimeSha256,manifestSha256}`. The manifest SHA is the exact restored file bytes, including its newline. Rust managed admission requires this binding for E2B and persists it into the workspace. The adapter checks the private template's exact name/default-build/buildCount-one before and after allocation; immediately before delivering the boot credential it checks the current template again and verifies runtime/manifest file hashes on the restored sandbox. A version change after create is an uncertain creation outcome, not authority to allocate again. The actual generated `TemplateWithBuilds` schema inherits `templateID`, `buildID`, `buildCount`, `buildStatus`, `public`, `names` and `aliases` from `Template`; the [primary response handler](https://github.com/e2b-dev/runtime/blob/78d5ff91515b58a9bd2d0b28b14f80428c63d15e/packages/api/internal/handlers/template_get.go#L95) maps its default build into `buildID`.

This is an **operational version pin** under the trusted sole infrastructure key. It cannot prevent an independent key holder from retagging between reads and switching back, and it is not an atomic or cryptographic provider build selector. The key must be limited to the reviewed operator flow; no reuse/rebuild/retag of the unique template is permitted. Observed version or restored byte changes fail closed before account/model credentials are delivered. Registration and cache selection must preserve the entire binding without synthesizing or dropping it. RAM-preserving resume, cold task restore, credentials, private checkout, tools, Stop/queue behavior and live cleanup remain separate acceptance gates.

## Finalization permission failure and source correction

The first reviewed template build failed during finalization with `managed_base_file_unsafe`; independent original-template lookup returned 404 after verified cleanup. No sandbox/model execution succeeded. The pinned provider [finalization script](https://github.com/e2b-dev/runtime/blob/78d5ff91515b58a9bd2d0b28b14f80428c63d15e/packages/orchestrator/pkg/template/build/phases/finalize/configure.sh#L95) runs `chmod -R 777 /usr/local`. The original strict ready helper correctly rejected that metadata. The source correction above preserves strict readiness and moves the root boot owner and seal outside that tree; it does not trust writable Python imports or relax restored artifact hashes. It is not yet a live E2B proof and authorizes no retry.
