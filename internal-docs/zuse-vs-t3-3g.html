Why first load favors T3

Zuse transferred 3.72 MB before readiness; T3 transferred 2.89 MB. Zuse's compressed WASM is still its biggest first-visit cost on this connection.

Why cached reload favors Zuse

Zuse's fingerprinted assets use immutable caching. The tested T3 build revalidated assets with ETags and no-cache. This likely explains much of the gap; the test does not isolate rendering speed.

Installed desktop traffic and browser startup are separate measurements.

Native integration

Native desktop chats and live agent panes now request a recent 32-message / 64 KiB window, load older messages on demand, and verify cached rows to skip unchanged history on reconnect. Chat and session lists request keyed changes. Model discovery starts with the active agent; other agents load when the picker opens. Full durable history and provider context remain available.

Native paired links use negotiated LZ4 compression, encryption and acknowledgment-based replay limits. Profitable frames from 256 bytes can now be compressed. Account connections receive the smaller history and list payloads, but do not use the paired LZ4 codec.

The comparison bars in this report measure browser flows. They do not measure native desktop startup, paint or a desktop-to-desktop T3 comparison. The native regression fixture covers a real encrypted paired connection with 1,500 messages, paging, resume and live updates without a 3G throttle. Native timing results remain unmeasured.

05

What T3 skips, and what Zuse adopts

Exact 0.1.7 release source, reviewed alongside the actual wire measurements.

Compress the transport

T3 uses HTTP compression and native permessage-deflate with a retained dictionary. Zuse now uses zlib-rs level-3 deflate with a per-connection dictionary and native browser streaming decompression. Ready envelopes are batched without a timer. Small messages stay plain; older clients remain compatible.

server.ts · http.ts → Zuse browser_io.rs / rpc_compression.js

Keep bulky output behind a read

T3 omits command output and successful file-diff bodies from routine updates. Both products passed the three-output fixture: all 98,382 source bytes remain available, while routine records contain summaries, metadata or references.

WireProjection.ts → Zuse already stores tool blobs and fetches their pages on demand.

Avoid sending the same body twice

T3 deduplicates bodies shared between messages and turn items, compacts records and can use ID tables. Zuse's transcript already uses append deltas. This change also omits unchanged history metadata; the client retains its existing pagination state.

orchestrationV2DedupedBodies.ts → Zuse rpc.rs / transcript.rs

Coalesce meaningful updates

T3 buffers paragraph boundaries, gates streaming updates over 400 ms and coalesces replaceable events over 50 ms. This trades fewer updates for later visible text. Zuse keeps incremental text, suppresses no-op frames and batches already-ready envelopes without adding a paragraph delay.

assistantStreaming.ts · ThreadLiveEventCoalescer.ts

Leave unneeded sidebar data out

T3 can omit idle subagents and older settled threads from its first shell snapshot, fetching them when needed. Zuse now sends keyed chat/session list deltas and suppresses unchanged snapshots. Its first list still includes all rows; initial selective sidebar paging remains a gap.

ShellStream.ts · OrchestrationV2SubscribeShellInput

Page old work and bound queues

T3 pages older history, defers large work sections and bounds pending live traffic by both items and bytes. Zuse now validates cached history to send only missing rows and applies an 8 MiB queued/in-flight output budget to direct, paired and account browser links, including paired relay sessions. One intact oversized response is admitted exclusively.

threadHistoryPaging.ts · LiveStreamBudget.ts

These are design findings, not claims that every T3 mechanism has been ported. Compression was added to Zuse's direct browser link; paired, account and relay framing retain their existing behavior.

06

Conditions, evidence & limitations

Recorded measurements, explicit boundaries and reproducible test commands.

How the two apps were compared

Matched startup benchmark

  • Chrome for Testing 151.0.7922.34, desktop viewport 1280 × 1000.
  • 50,000 bytes/s down, 25,000 bytes/s up, 400 ms DevTools HTTP latency.
  • Three cold samples and three fully warmed reload samples per app.
  • Empty workspaces; authentication and T3 onboarding completed before timing. Initial onboarding-contaminated T3 trials were excluded.
  • Both apps negotiated Brotli. Encoded HTTP bytes include headers through readiness plus one second; WebSocket data is counted separately.
  • Warm-cache preparation ran without throttling until requests settled, then 3G conditions were restored.

Matched chat follow-up

  • Three paired runs per product, alternating which app runs first.
  • Same 1,500 alternating user/assistant messages; exact canonical text and roles verified.
  • Zuse history is imported; T3 history is inserted into a stopped disposable projection database. The two seed paths differ.
  • Real composer, history buttons, provider adapters, Stop and reconnect. Forty chunks at 50 ms intervals; completed paragraphs every five chunks.
  • Native socket compression remains enabled. The loopback proxy meters actual encoded bytes, preserves TCP order and applies shared directional rate limits.
  • Application shell downloads are excluded from runtime. Desktop CPU, no packet-loss or mobile-radio simulation.

Build identities and cache-policy differences

T3 measured release: 0.1.7, commit 322f6544dfad0a3c8a0c8cbecf2c7f7874b14268. The installer verified release SHA256SUMS. Hashed entry JavaScript and the Inter font returned Cache-Control: no-cache with ETags.

Zuse startup build: commit abd74d19c6f3acfd3308b05ad141928e71276439 plus uncommitted slow-network optimizations. Fingerprinted assets use immutable caching. See the exported data for the exact WASM identity.

Zuse runtime build: Current-main CI qualification: after the port, the existing localization and offline CJK fonts yield 8,354,245 aggregate Brotli bytes (about 167 seconds of transfer alone at 50,000 B/s). The release cap is 9 MiB. Startup charts retain the earlier pre-localization build and are not current-main timings.

Validation results and known limitations

Browser release and native engine builds passed; the matched runtime uses the debug native engine described above. Compression validation passed six JavaScript cases, two focused transport tests, five history-window tests and seven transcript UI tests. Keyed-list integrity and command-tail regression tests also pass; native RPC transport coverage passes 34 tests. The complete serve suite passed 30 tests; existing RPC coverage includes one ignored test. The full viewport suite recorded 45 passes and one previously recorded plugin-form mouse-focus failure at plugin_setup.rs:871.

Build matching browser and engine binaries, then run with Node 22+ and a WebGPU-capable Chromium:

CHROME_BIN=/path/to/chrome ZUSE_RUNTIME_ONLY=1 \
  ZUSE_NETWORK_HISTORY_ROWS=3000 ZUSE_NETWORK_SOCKET_RTT_MS=400 \
  ZUSE_RUNTIME_BLACKHOLE=1 node scripts/acceptance/slow-network.mjs

# Active-agent disconnect run:
CHROME_BIN=/path/to/chrome ZUSE_RUNTIME_ONLY=1 \
  ZUSE_NETWORK_HISTORY_ROWS=3000 ZUSE_NETWORK_SOCKET_RTT_MS=400 \
