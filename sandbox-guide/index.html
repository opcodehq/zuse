An illustrated guide · Linux / KVM / Firecracker

One machine.
Many worlds.
How sandboxes work.

Your code can share a server with a stranger’s code without sharing access to their memory or files. Here is what makes that possible—and what makes it economical.

A sandbox is a restricted execution environment, not one specific technology. This guide follows a typical Firecracker microVM service. Provider architecture and product guarantees vary.
01 / Location

There is a real computer underneath.

A provider operates physical servers in a data center. Each server has CPU cores, RAM, storage, and networking. A host operating system allocates these resources to workloads.

↓ chooses a host

Their guest Linux kernel

Shared physical hardware; separately controlled execution and access.

The host controls the physical server. A guest is the operating system inside a VM. Your shell usually lives in the guest. Classic Firecracker uses Linux’s KVM interface; running inside another VM requires suitable nested virtualization support.

02 / The boundary

“Sandbox” does not always mean “VM.”

Select an architecture to see which component handles an application’s system calls. A system call is a request to the operating system—for example, to open a file or create a socket.

Application → shared host Linux kernel → hardware

Separate views, shared kernel.

Namespaces isolate views of processes, mounts, users, and networks. Cgroups account for and limit resources. Permissions, capabilities, and seccomp restrict operations. The application still asks the host kernel to perform its system calls.

Security boundary: the host kernel and its configured isolation policies.

An Ubuntu container image supplies userspace files and programs. It does not boot its own Ubuntu kernel. A Linux VM has its own running kernel.

References: Linux namespaces · gVisor security model.

03 / Execution & addresses

The CPU runs your code. Hardware enforces the boundary.

Most guest instructions execute directly on the physical processor. Firecracker does not interpret each addition or memory read. Hardware virtualization lets the host run a guest while retaining control over the machine.

CPU execution

A vCPU is scheduled work.

A virtual CPU has execution state, including registers and an instruction pointer. Its host thread receives time on a physical CPU. Other vCPU threads can use that CPU at other times.

Core over time:
[ VM A ][ VM B ][ VM A ]

A vCPU is not necessarily a dedicated physical core.

Host intervention

A VM exit transfers control.

Certain configured events stop guest execution and return control to the host. KVM handles some; others need Firecracker’s device implementation.

Guest → VM exit → handle → resume

An ordinary guest syscall can stay entirely inside the VM.

Firecracker opens /dev/kvm, creates a VM, registers guest memory, creates vCPUs, and runs them with KVM_RUN. KVM is the host kernel component managing hardware virtualization. Firecracker is the userspace virtual machine monitor.

Memory has two levels of address translation.

Guest virtual address
↓ Guest page tables
Guest physical address
↓ Host-controlled second-stage translation (EPT / NPT on x86)
Host physical RAM
VM A · address 4096→RAM page X
VM B · address 4096→RAM page Y

The same guest address can map to a different physical page in each VM.

Guest root can edit guest page tables, but cannot thereby edit the host’s second-stage mappings. The processor checks address translation during memory access. Firecracker does not inspect every load or store.

04 / Input & output

A virtual device connects two worlds.

A guest usually gets virtual devices rather than direct ownership of a physical SSD or network card. Virtio supplies an interface designed for virtualization: the guest posts requests in queues, and a backend processes them and reports completion.

Disk write

Your file becomes block requests.

write("hello.txt")
↓ Guest filesystem
Virtio block request queue
↓ Firecracker backend
Host disk backing file
↓ Physical storage

The guest sees a disk such as /dev/vda. The host can represent that disk as a file.

Network packet

Your socket becomes packets.

Guest application
↓ Guest TCP/IP stack
Virtio network device
↓ Firecracker → TAP interface
Host routing & firewall
↓ Physical network

TAP lets a userspace program exchange Ethernet frames with host networking.

Network access is a separate policy decision. A private IP address alone does not stop a guest from contacting its neighbors. The provider must enforce allowed routes and destinations. Likewise, it must expose only the intended disk images and host–guest channels.

06 / Economics

Cheap compute is mostly well-used compute.

Many sandboxes spend time waiting for humans, APIs, models, or disk I/O. A provider can schedule other workloads during those gaps. This is why more configured vCPUs than physical cores can be useful—until too many workloads become busy at once.

Capacity model · illustrative, not a benchmark

This imaginary host has 64 physical cores and a 224 GiB guest-memory budget. Each sandbox receives 1 GiB RAM and one vCPU. The model assumes equal, sustained CPU demand and ignores VMM overhead and scheduling costs.

32cores of requested CPU time
160GiB of guest RAM budgeted
2.5×configured vCPUs / core

CPU demand fits: 32 of 64 cores. Headroom remains for bursts.

Average utilization hides correlated bursts. Capacity planning also needs peak demand, latency targets, I/O, and safety margins.

CPU waiting time is shareable. Retained RAM is still occupied. Pausing a VM stops execution but does not automatically free its memory. Reclaiming it needs an additional mechanism, such as snapshotting and unloading, ballooning, or swapping, each with tradeoffs.

Lower overhead

Small device models, minimal guest systems, shared clean templates, and copy-on-write storage reduce per-instance work and storage duplication.

Shorter resource occupancy

Destroying finished jobs and unloading idle environments returns capacity to the pool. Keeping prebooted VMs ready instead trades capacity for lower latency.

Firecracker advertises sub-125 ms boot and under 5 MiB VM overhead under its stated conditions. That is not total guest RAM, nor a promise that your application and terminal are ready in 125 ms.

07 / Resume instead of rebuild

A snapshot is a saved execution state.

A provider can boot a clean guest, load a runtime, and snapshot it at a ready point. New instances can restore that state instead of repeating initialization.

Boot → initialize runtime → pause → save template
↓ restore into separate instances
Instance APrivate changes
Instance BPrivate changes
Instance CPrivate changes

Clean snapshot memory can be privately mapped and read on demand; modified pages become private copies.

Firecracker saves memory and VM/device state. Disk images are managed separately by the operator. A fast restore may defer memory loading until pages are accessed, so the first useful work can still incur page faults and storage latency.

Cloning also copies state that may need refreshing: identifiers, secrets, random-generator state, and network configuration. Existing connections are not guaranteed to survive restoration. A template must be designed for safe reuse.

Reference: Snapshot behavior and security.

08 / Trust

Isolation is enforced in layers.

A guest kernel is powerful inside its VM. The host treats guest-controlled device requests as untrusted. Firecracker’s small device surface reduces the amount of code processing those requests, while additional host restrictions limit the consequences of a VMM exploit.

Untrusted application & guest kernelGuest root controls this world.
Hardware virtualization + KVM + VMMConstrain memory, privileged execution, and virtual devices.
Host process confinementJailer, dropped privileges, restricted filesystem, seccomp, namespaces and configured resource limits.
What if my code runs an infinite loop?

It consumes available CPU time. Host scheduling and configured quotas limit the allocation. It can still create contention on shared resources, so performance isolation needs deliberate engineering.

What if I delete everything as root?

You can damage writable disks exposed to your guest. Guest root does not automatically gain access to the host filesystem or another guest’s disks. Exposed host mounts and incorrectly scoped storage can undermine that separation.

What if Firecracker itself is exploited?

The jailer confines the host process and drops privileges; seccomp restricts its host syscalls. These layers reduce available actions after compromise. They are not a proof that every exploit is contained.

Is a VM perfectly secure?

No. VMM and kernel vulnerabilities, misconfiguration, hardware side channels, and service authorization bugs remain possible. Regular kernel, VMM, and microcode updates are part of the isolation system.

References: Jailer · Production hardening.
